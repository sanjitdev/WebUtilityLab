Technique 01

First Principles

Drill · Bedrock

We kept going down. Each layer answered one more "but why?" until we hit something the user could falsify. The user reframed the early questions fast — they trust the browser-can-do-anything claim — so the real bedrock turned out to be about tolerable latency, not capability.

L1
Surface question

"Can the browser do anything a computer can?"

The user closes this immediately: Photopea, Photoshop-on-Web, and Figma settle the capability question. We are not contesting it.
L2
Closer to bedrock

"But is the privacy claim verifiable?"

Yes — the user can open DevTools, watch the Network tab, and see no API calls. The structural promise is honest if the discipline holds.
L3
Bedrock

"What does the user actually need to perceive?"

Coach · reframing

The bedrock isn't a capability claim, it's a latency-tolerance claim: the browser must do in tolerable time what a backend would have done. The doc is silent on first-10-second experience.

User · falsifiable anchor

10s acceptable, 10min not. Sets a falsifiable, user-perceived bedrock instead of a developer-intuition one.

L4
Operational rule (ship rule)
A Ship Rule

5s-to-meaningful-result, with honest estimates above it.

Coach · operationalization

Every tool shows a meaningful result by 5s. Operations >5s are progressive/async. This would naturally disqualify Local LLM tools, slow crawlers, and full ZIP scans from the MVP.

User · refinement

Estimates from data size before processing. Show a band ("~10s ±30%"), not a fixed number. Refuse jobs whose upper bound exceeds threshold. Margin of error is acceptable; deception is not.

L5
Structural bedrock

"Is the platform actually stateless?"

User · reframing MVP

Stateless one-shot transformations are the goal — not a stepping stone. Upload → process → download → leave. Like a screwdriver. SaaS features (history, accounts, sync) are explicitly out of scope and not a loss.

Coach · brand asset

"It costs you nothing because it doesn't remember you." Stateless isn't a constraint; it's the brand.

L6
Hidden risk the doc underweights

"Where is the privacy risk actually located?"

Coach · diagnosis

The privacy risk lives in the surrounding 30% — analytics, error reporters, fonts, CDN logs, transitive deps. Local-first is architecture, not discipline. The two are not the same thing.

Technique 02

Reverse Brainstorming

Failure Gallery

How could WebAnvil fail? Each card is a failure mode we named. The user picked the scariest ones as the "positioning invisible to the user" failures — the kind that lose before the product gets a fair hearing. Coach surfaced one the user didn't list, and the cross-link idea became the headline salvage.

F5 · Adopted

Workflow tools that look like single-purpose tools

Users have a workflow, not a tool in mind. MVP's 5 separate tools = 5 Google searches = 5 competitors.

Salvage → Mechanism A + B File-in-hand handoff (file metadata, day 1) and result-page "next, you might want to..." links (day 1, all tools, trivial cost).
F8 · Adopted

MVP indistinguishable from 100-tool sites

No visible "this is faster than the alternative" promise, no side-by-side, no depth affordance. Tab-comparison kills the product.

Salvage → visible proof A "Compare" page for deep tools: same dataset, same operation, our result vs. theirs. Visible proof, not claims.
F5b

No "show me the depth" affordance

Depth visible only after first use — which is the moment we lose the user. The landing experience must show depth on first interaction, not in a docs page.

F8a

No "faster than the alternative" promise

Performance is invisible in tab-comparison. The user can't perceive the difference until they upload their file — and by then they've already bounced.

F8b

No side-by-side with competitors

Without a side-by-side proof point, the user picks the tool they know. Same data, same operation, our result vs. theirs.

F9 (Coach) · Adopted

Tools fail in isolation

User has a workflow, not a tool in mind. MVP's 5 separate tools = 5 Google searches = 5 competitors. The product loses before the workflow gets assembled.

Salvage → Cross-link at result level "Next, you might want to..." static links at the result page. Stateless, fits the screwdriver model, zero new infrastructure.
Mechanism D · Deferred

PWA-as-persistent-environment

IndexedDB recent-files, "last 5 tools" sidebar, persistent shell. Useful, but breaks the stateless principle and adds maintenance.

Salvage → Post-MVP After 5 stateless tools are validated. Not day-1.
Mechanism C · Rejected

Same-tab sessionStorage handoff

Could carry state across tools, but breaks expected "open in new tab" UX and undermines Mechanism D's coherence if D ships later.

Salvage → Reject Don't ship a half-step toward a model we're not committing to.
Technique 03

Question Storming

12 questions · 2 heavy

Twelve questions, no easy answers. The user then singled out the heavy ones — the questions hiding the real problem. Two glow: Q2 (repeat-visit / brand memory) and Q6 (why does this exist when competitors already have these tools?). The answer turned out to be one word that had to be operationalized: craft.

Q1 Who is the user when they arrive? (User persona not defined.)
Q2 · Heavy Why would a user prefer WebAnvil on a second visit? Brand memory and repeat-visit reason are not defined.
Q3 What does "done" look like for the user, not the platform?
Q4 What does the user have to believe about WebAnvil before uploading their file?
Q5 What is the second thing the user does? (Real measure of stickiness.)
Q6 · Heavy Why does WebAnvil exist when iLovePDF / FreeLabTools already have these tools? The hardest, most honest question.
Q7 What will the doc NOT mention that would be obvious in a year?
Q8 What user need is WebAnvil's LEAST attentive to? What is absent from the doc?
Q9 What is the doc's MOST undefended claim?
Q10 Who would HATE WebAnvil, and why?
Q11 What is the first thing the user sees, and what does it make them feel?
Q12 If only ONE tool could be shipped, which one, and why?

★ heavy questions — hiding the real problem

User · the heavy questions

The user picks Q2 + Q6 as the load-bearing pair. Q2: why a second visit. Q6: why exist at all when competitors already have these tools.

Coach · the operational answer

The un-copyable thing isn't "love" — it's the operationalization of love as craft practices: kind error messages, graceful edge cases, teaching empty states, refusing bad jobs, honest changelogs, visible trust signals, public postmortems.

Process decides

The user picked Blue from the six. Blue decides what we actually do — not what we feel, what we fear, or what we hope. The other five hats hang around it as witnesses.

Blue · Process · The Hero

What we actually do.

Decision · Definition of Done (7 items, all falsifiable)

(1) edge-case test suite green incl. BOM/NaN/BigInt/deep/50MB, (2) privacy audit clean — no network calls, analytics, fonts, CDN, transitive-dep leaks, (3) three outside users use it on real work files without surprise, (4) honest changelog written before bug, (5) solo half-day "try to break it" finds no crash, (6) empty state teaches, (7) every error msg has explanation + next-step.

Applies to EVERY tool, not just "the 1."

Technique 05

Job to Be Done

User hires the tool

A user "hires" JSON Surgeon for a specific job. The first-visit job is the priority. The right success metric is not parse success or feature count — it's time-to-competence: the moment the user says "I have my answer and trust the answer."

The User's job

"I have an API response I don't trust. Make me confident it's what I think it is, and let me see what to do with it."

First-visit job, chosen by the user as priority for JSON Surgeon.

SUCCESS METRIC
Time-to-competence
page load → "I have my answer and trust the answer"
→ HIRES
JSON Surgeon · the hire

Surface the one worry: what's wrong with this response, and what does the developer need next.

Three-pane framing: input · diagnosis · next step. User called this "alright — fits without dominating." Not a pushback, not a strong endorsement. Keep, but don't center on it.

ANTI-METRICS
feature count, parse success rate
JOB STATEMENT
When I have a messy API response, I want to see and trust the diagnosis, so I can decide what to do next without shipping a tool, paying for a service, or waiting on someone else.

Technique 08

Pre-mortem

12 failure moments · a year from now

It's 12 months from now. WebAnvil failed. We walk backwards from the obituary. Each moment names the failure and the prevention. The privacy-death moments (PM-3, PM-10) and the discoverability moment (PM-6) deserve the most weight — they're the brand-killers.

PM-1

The depth never lands.

First-time user opens JSON Surgeon, sees a blank textarea and a "Format" button. Never realizes the tool can do 11 things. Thinks "another JSON formatter" and leaves.

PreventionLanding experience must show the depth on first interaction, not in a docs page.

PM-2

The error message is the brand.

User pastes a JSON file with a trailing comma. Tool says "Invalid JSON." No explanation of which line, what the rule is, how to fix. User assumes the tool is buggy, switches to a competitor with kinder errors.

PreventionEvery error has explanation + next-step (DoD item 7).

PM-3

The transitive dependency phones home.

6 months in, a transitive npm dependency ships a version that phones home. WebAnvil is now uploading data it promised not to. Privacy researcher tweets the network capture. Brand is over.

PreventionThe cheap privacy baseline: no analytics, no fonts, no CDN, no transitive deps with side-effects, dependency-audited on every release.

PM-4

50MB JSON hangs the tab.

User has a 50MB JSON file. Tool hangs the tab for 40s. User closes the tab, writes a Reddit post: "WebAnvil is unusable on real data."

PreventionPre-flight estimation says "this is too big for your browser" and suggests sampling, not processing.

PM-5

The solo maintainer disappears.

Project's only contributor gets a new job in month 8. Repo is private, code is uncommented, architecture is in one head. Project goes dark for 2 months, then archived.

PreventionCode is readable, comments explain WHY, contributor guide exists, repo is public from day 1.

PM-6

The second visit never comes.

User has a great experience, returns 3 weeks later. Searches "WebAnvil." Can't find the tool. Goes to JSON formatter on the first result. Never comes back.

PreventionThe brand is SEO-tested before launch. Tool URLs are stable, named, and linkable.

PM-7

The 2019 MacBook Air can't load it.

User on a 2019 MacBook Air opens WebAnvil. JSON Surgeon takes 12s to load (WebAssembly module). User has been on a competitor site for 2s. Even with all the differentiation, perceived speed kills the first impression.

PreventionProgressive enhancement — show the input immediately, lazy-load WASM. The user's first byte is fast even if the work isn't.

PM-8

The page describes features, not jobs.

Landing page describes what each tool does ("Format, validate, transform JSON") instead of what the user is hiring it to do. The user never makes the leap from "I have a problem" to "this tool is mine."

PreventionEvery tool page leads with the job, not the feature list.

PM-9

Tab-comparison loses.

MVP tools compete directly with Photopea, jsonformatter.org, DiffChecker. A user comparing tabs sees WebAnvil's CSV Rescue next to Papa Parse. Without a side-by-side proof point, the user picks the tool they know.

PreventionBuild a "Compare" page for the deep tools — same dataset, same operation, our result vs. theirs. Visible proof, not claims.

PM-10

DevTools proves the lie.

User opens DevTools, sees a Sentry error reporter making a network call. The privacy claim is a lie, in the DevTools, in 30 seconds. User screenshots, posts to HN. The brand dies in 24 hours.

PreventionPrivacy audit is reproducible by a stranger. Open the source. Show your work.

PM-11

No way back.

User uses the tool. It works. The user is amazed. They want to use it again. They have no way to save the result, no way to come back to the tool, no way to share the URL with a state. Each visit is fresh friction.

PreventionThe "next, you might want to..." link is the brand's handoff. Not state — invitation.

PM-12

The success kills it.

The project succeeds. 50 tools, real users, real traction. The maintainer burns out. There is no successor. The site goes dark. The repo is archived.

PreventionDesign from day 1 for a successor — public repo, contributor docs, architecture that doesn't require the original author, and a 1-paragraph "why this exists" that someone new can read and own.

Craft · The Un-copyable Differentiator

"Craft" — operationalized, not just claimed.

The seven practices that turn "we care" into something competitors can't copy.

  1. Kind error messages — explanation + next-step on every error.
  2. Graceful edge-case handling — BOM, NaN, BigInt, deep structures, 50MB files.
  3. Teaching empty states — first-time users learn the tool, not just see it.
  4. Refuse jobs that can't be done well — pre-flight estimation, honest "this is too big."
  5. Honest changelogs written before the bug, not after.
  6. Visible-at-moment-of-trust privacy signal — not a privacy-policy page.
  7. Public postmortems — failures visible, history not erased.
